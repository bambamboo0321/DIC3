# Introduction

固定工作場域中的飲水與飲食紀錄，仰賴使用者在事件發生時辨認攝取項目、取得份量並完成輸入。手動表單可承接多種情境，但逐次填寫與回想份量會增加操作成本。若使用者事後補登，紀錄也可能欠缺份量依據，難以核對跨日統計。本研究以實驗室與辦公室為場景，探討如何由桌面感測減少輸入步驟，並使使用者仍能確認、修正與追溯紀錄。

既有飲水研究已使用容器附掛加速度計與商用智慧水瓶取得飲用量估計。Griffith 等人以容器運動特徵估計單次飲用量。Cohen 等人比較商用水瓶，發現單次誤差、累積偏差與漏記表現因裝置而異。Baker 等人則在球隊訓練中以重量法對照光學瓶蓋的估算。辦公室飲水資料集 OHM 使用容器上的 IMU 記錄多種操作，呈現飲水事件與其他容器互動均須列入評估的理由。這些工作提供量測與評估參考，固定杯墊的可用訊號則受限於杯子接觸秤面的時段。[[1]](related-work.md#ref-1) [[2]](related-work.md#ref-2) [[3]](related-work.md#ref-3) [[4]](related-work.md#ref-4)

杯墊量到的減重可由飲用、倒水或灑出造成。重量差可建立候選事件，實際行為仍須透過獨立觀察評估，必要時由使用者確認。飲食紀錄則涉及食品辨識、可食份量及成分資料的適用性。Li 等人比較人工與影像輔助紀錄，觀察到混合與文化特定菜餚的估算差異。Fridolfsson 等人指出大型語言模型（LLM）由照片估算時，份量與營養偏差會隨樣本條件變化。López Torres 等人的稽核發現，營養輸出的內部一致性可以和同類輸入的再現性不足並存，且該稽核未以獨立營養真值驗證。對固定場域而言，去皮秤重可提供可查核的份量基準，配方及食品條目的匹配仍會影響估算。[[5]](related-work.md#ref-5) [[6]](related-work.md#ref-6) [[7]](related-work.md#ref-7)

本研究提出 SmartIntake，以 Raspberry Pi 4 連接飲水杯墊與食物秤，兩者各使用一組 Load Cell 與 HX711。飲水 FSM 比較杯子拿起與放回前後的穩定重量，對一般候選自動記錄並保留撤銷及修正，對不確定事件由 Discord 請使用者確認。場域外飲水採手動補登。飲食模式分為單項食物去皮秤重與整餐估算。後者優先使用可靠淨重與適用的餐點資料，餐盒重量未知時採有來源的每份參考值。營養估算以臺灣食品營養成分資料為優先，USDA FoodData Central 為補充。三位測試使用者透過 Discord 切換兩秤共用的 Active User Session，事件沿用開始時的 Session ID、User ID 與 Session Version。參見[技術設計](../../design.md)。[[8]](related-work.md#ref-8) [[9]](related-work.md#ref-9)

SmartIntake 以 n8n 建立 Domain AI Agent，透過 LLM Tool Calling 解析問題、選用六項唯讀工具並組織跨日分析。FastAPI 執行身分驗證、授權、資料查詢與確定性計算，回傳可追溯的期間、單位及來源。τ-bench 將工具使用與領域規則納入評估。本研究將此概念用於個人攝取查詢，檢驗同一個回答能否同時滿足工具選擇、數值、來源與授權要求，並能妥善回應缺資料情形。[[10]](related-work.md#ref-10)

研究規劃五項驗證。E1 以獨立參考重量測試兩秤的重量準確度、穩定時間與漂移。E2 比較簡單重量差、FSM 與 Discord 確認流程，分別評估自動分類及人工修正後的紀錄。E3 檢查多人切換時兩秤的歸屬。E4 以交叉平衡的同一受試者設計，比較手動手機表單與半自動紀錄的操作效率。E5 使用至少 30 個固定情境評估 Agent 的可靠性。參見[實驗計畫](../experiments/experiment-plan.md)。

預期貢獻包括固定場域的雙秤紀錄設計、可追溯的多人歸屬及營養估算，以及一套檢驗資料與 Agent 回覆的實驗方法。兩秤三人屬小規模原型評估，量測限於可取得穩定讀值的情境。杯墊不觀察離杯期間的動作，整餐參考值也會受實際配方差異影響。研究範圍聚焦於 IoT 與 Domain AI Agent 的系統整合及實驗驗證，成效與適用範圍將依實驗結果判定。
